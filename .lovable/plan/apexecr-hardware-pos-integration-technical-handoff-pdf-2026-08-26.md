It will document the integration exactly as it exists today, compare it with the supplied ApexECR Web Integration Specification v1.08 and AFS BRD, and clearly separate verified implementation facts from suspected defects and items requiring AFS confirmation.

### 8. Transaction lifecycle and financial records
- Server-to-server call into `process-payment` and internal-token protection.

- How completed records feed existing reports and how receipt delivery proceeds by SMS/WhatsApp.
- Failure behavior if terminal approval succeeds but transaction persistence fails.

### 9. Verified risk and defect register
Document, with file/line evidence and severity, the current reliability gaps:
- Cancellation is issued concurrently while the original long-running SALE remains active; the kiosk does not abort or coordinate that request.
- Cancellation success is inferred from web-service status only and does not verify that the terminal returned to idle.
- UI timeout does not terminate or reconcile the backend SALE; a late approval can still be processed.
- Enquiry exists as an action but is not automatically used for unknown/timeout recovery.
- The local stale-session flag is written and cleared but no longer controls recovery before a new SALE.
- A successful terminal approval can be shown even if `process-payment` fails or returns a non-success status, because the persistence response is not enforced.
- Failed/declined terminal responses are also inserted as transaction records; describe the intended versus actual reporting effect.
- Six-digit invoice numbers are derived from only part of a UUID and can collide; no persisted idempotency/session state guards the Apex request itself.
- A 60-second in-memory configuration cache can temporarily retain edited credentials or terminal pairing.
- Admin “Verify Terminal” checks service/SOAP acceptance but explicitly cannot prove terminal availability.
- Generic fetch/abort handling and edge-runtime duration constraints can obscure whether the command reached AFS.

### 10. Diagnostic playbook for the reviewing engineer
Provide a step-by-step evidence collection checklist:
1. Capture client timestamp at Confirm.
2. Capture backend request arrival, config lookup, SOAP dispatch, and response timestamps.
3. Obtain AFS correlation/server logs for the same sanitized reference.
4. Confirm WSDL binding, endpoint, SOAPAction, namespaces, and exact operation contract.
5. Confirm MID/TID/key pairing and terminal online/idle state.
6. Test SALE approval, decline, donor cancel, terminal cancel, app timeout, network interruption, duplicate retry, late response, and forced EnquiryByRef.
7. Reconcile every approved terminal event with one and only one database transaction.

Include expected observations, failure interpretation, and the minimum logs AFS should return.

### 11. Recommended correction architecture
Describe a robust target design without changing the application in this task:
- Persisted payment-session state machine with one active session per kiosk/TID.
- Immediate SALE dispatch with explicit command acknowledgement separate from final card result where supported by AFS.
- Coordinated cancellation tied to a session/reference, not only “cancel last request.”
- Deterministic idempotency and automatic enquiry after timeout/unknown outcome.
- Never permit retry until the prior session is definitively approved, declined, cancelled, or reconciled.
- Transaction persistence as a required part of the approved flow, with retry/outbox protection.
- Structured correlation IDs and latency telemetry across app, backend, AFS, and terminal.
- Note that simultaneous UI appearance and terminal response cannot be guaranteed by frontend code alone; the achievable target is immediate SOAP dispatch plus measured AFS/terminal acknowledgement.
